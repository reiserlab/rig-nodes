ezmsg and rig frameworks

We looked at ezmsg, a pure-Python message-passing framework for signal processing, as a companion to or replacement for ROS 2 on our rigs. While doing that, we wanted to compare the other related packages in this space.

ROS 2 stays the rig graph. We do not plan to use ezmsg on the rigs for now. Of the other systems, LSL and Harp each solve a problem we still have open: aligning clocks across machines and devices.

Summary

  • ezmsg has no relationship to ROS 2: no shared transport, message format, tools, or bridge.
  • Between two Python processes, ezmsg is 1.2 to 5 times faster than ROS 2 for 1 to 8 MB messages, and about equal for the small messages our rigs send today.
  • The cost on the ROS 2 side is the Python client (rclpy), not the transport. A C++ subscriber on the same transport is faster than ezmsg.
  • Replacing ROS 2 would cost us MCAP recording, Foxglove, the typed message contract, and non-Python clients.
  • We do not plan to use ezmsg on the rigs for now, also not as a library inside one node. The stable release does not run on the workspace's Python (below), and its gain is for large arrays between Python processes, which is not a rig need. We can revisit this when a stable ezmsg release runs on the workspace's Python.
  • rmw_iceoryx, a zero-copy transport for ROS 2, would not help our rigs as they are. Its zero-copy path is fast (0.13 ms for 8 MB) but needs fixed-size messages and C++ nodes. For sensor_msgs/Image, which we send from Python, it was 2.5 to 5.3 times slower than rmw_zenoh at 1 MB and above.

ezmsg 3.9.0, the latest stable release, is not compatible with our rig workspace as it is defined.

The workspace pins Python 3.14 (RoboStack Lyrical). ezmsg 3.9.0 fails on Python 3.14 and on 3.15, the newest Python, as soon as a pipeline starts. It runs on Python 3.12 and 3.13. Every ezmsg figure on this page was measured on Python 3.12.

The install does not warn. pip installs ezmsg 3.9.0 on Python 3.14 and downgrades nothing. The failure comes at run time.

The fix is only in the 3.10.0 pre-releases. 3.10.0b5 ran on Python 3.14 and 3.15 in a short check on 2026-11-19.

Using ezmsg with the rig software today means one of three things:

  • An ezmsg pre-release in the workspace.
  • The workspace on Python 3.12. This affects all other installed software: ROS 2, rmw_zenoh, our rig packages, and every other package would move with it.
  • ezmsg in its own environment, which has no ROS 2. A node that uses ezmsg would then need a second ROS 2 install on Python 3.12.
C++ subscriber on the lab Windows PC (ww18)

With shared memory on, the C++ rosbag2 recorder receives an 8 MB message in under 0.2 ms

0.18–0.19 ms 8 MB at 30 Hz, median (5.2–5.6 ms with shared memory off)
0.11–0.12 ms 2 MB at 135 Hz, median (1.3 ms with shared memory off)

The 99th percentile stayed at or below 0.4 ms, and nothing was lost below 8 MB at 200 Hz. On the same PC, a Python (rclpy) subscriber took 11–12 ms for the same 8 MB message, about 60 times longer. ezmsg's best result between two processes was 0.73 ms, measured on a Mac.

So ROS 2 with rmw_zenoh is not the bottleneck for large frames. Where speed matters, a C++ node on the existing graph gets it, with no second framework.

Test system: ww18, Intel Core Ultra 9 285K, Windows 11 25H2, measured 2026-10-21/22, two runs each. The recorder figure spans rmw publish to recorder receive; the publisher's Python-side conversion is not included.

rmw_iceoryx, rmw_zenoh, and ezmsg on one Linux machine

rmw_iceoryx is not a framework. It is another transport under ROS 2, in the slot rmw_zenoh fills on our rigs, built on Eclipse iceoryx. The publisher writes a message into shared memory and the subscriber reads the same memory. We built it under ROS 2 Jazzy and measured it, rmw_zenoh, and ezmsg on the same Linux machine with the same message sizes.

  • rmw_iceoryx with fixed-size messages and the C++ loan API takes 0.09–0.14 ms at any size. That matches ezmsg inside one process, and rmw_zenoh took 2.0–6.8 ms for the same 2 MB and 8 MB messages between the same C++ nodes.
  • ezmsg is the fastest way to move a large array between two Python processes. With numpy arrays of 1 to 8 MB it was 4 to 7 times faster than rmw_zenoh, and it was also ahead at 64 kB.
  • rmw_iceoryx with sensor_msgs/Image is the slowest of the three from 64 kB up. At 1 MB and above it took 2.5 to 5.3 times as long as rmw_zenoh, and the publisher could not hold 8 MB at 30 Hz or 2 MB at 135 Hz.
  • Our rigs use that slow path. They send sensor_msgs/Image, a variable-size type, from Python nodes. Reaching the fast path means a new fixed-size frame message and C++ nodes on both ends.
  • rmw_iceoryx is one host only. iceoryx is shared memory between processes on one machine. rmw_zenoh can also cross the network, which the clock-alignment work assumes.
  • rmw_iceoryx did not build as shipped. RoboStack has no package, and the jazzy branch (last commit January 2024) does not compile against the iceoryx 2.95.8 that RoboStack Jazzy provides. We built iceoryx 2.0.6 from source beside it.
  • ezmsg 3.9.0 did not run on Python 3.14, the version RoboStack Jazzy installs here, so it ran in its own Python 3.12 environment. ezmsg 3.9.0 is therefore not compatible with our Python 3.14 workspace; the fix is only in the 3.10.0 pre-releases.
  • rmw_iceoryx has gaps in ROS features. Its README lists ros2 param list and pub/sub events as unsupported, and ros2 bag as untested. We did not test recording.

System by system

ROS 2 with rmw_zenoh

What every Reiser Lab rig runs today, packaged in rig-nodes.

Strengths

  • A written, typed contract between independently started device nodes.
  • MCAP recording and Foxglove viewing with no code of ours.
  • C++ subscribers are very fast: 8 MB in under 0.2 ms on the lab Windows PC.
  • Commands, replies, and status follow one pattern for every device.

Weaknesses

  • Heavy to install; we solved this with a CI-built package channel.
  • The Python client is slow for large frames (11–12 ms for 8 MB on Windows).
  • No built-in clock alignment across machines.
  • Few neuroscience devices ship a ROS driver, so we write adapters.

ROS 2 with rmw_iceoryx

An alternative transport for the same ROS 2 graph, built on Eclipse iceoryx: publisher and subscriber share one block of memory, with no copy. Measured by us on one Linux machine.

Strengths

  • True zero copy: 0.09–0.14 ms from 64 kB to 8 MB between C++ nodes, against 2.0–6.8 ms with rmw_zenoh for 2 MB and 8 MB.
  • Keeps the ROS 2 contract: the same .msg files, nodes, and most ros2 tools.
  • Switching is a setting (RMW_IMPLEMENTATION), not a rewrite, for nodes that do not need zero copy.

Weaknesses

  • Zero copy needs fixed-size message types and the C++ loan API. For sensor_msgs/Image from a Python node it was 2.5 to 5.3 times slower than rmw_zenoh at 1 MB and above.
  • One host only, which closes the path to a multi-machine rig.
  • Needs the RouDi daemon running before any node starts.
  • Incomplete and quiet: no ros2 param list, no pub/sub events, ros2 bag untested, last commit January 2024. The jazzy branch needed an older iceoryx built from source.

LSL (Lab Streaming Layer)

A C++ library with bindings in six languages, a recorder app, and the XDF file format.

Strengths

  • Time synchronization is built in and designed for sub-millisecond accuracy on a local network.
  • Raw timestamps and every clock-offset measurement are stored, so alignment can be redone offline.
  • Many vendors ship LSL apps for EEG, eye tracking, motion capture, and audio.
  • Light to install and available from MATLAB.

Weaknesses

  • Data streams only: no commands, replies, or device control.
  • No structured message types, only flat channels.
  • TCP transport with no shared memory, so it is a poor fit for camera or imaging frames.
  • XDF is less widely supported by viewers than MCAP.

Bonsai and Harp

Bonsai is a visual language built on reactive programming (.NET). Harp is a binary protocol, a set of common device registers, and a clock synchronization protocol for microcontroller devices.

Strengths

  • Fast to assemble a camera-tracking or closed-loop behavior experiment without writing code.
  • Packages for cameras, microcontrollers, and open hardware.
  • Harp devices timestamp every event in hardware on a shared clock, so data is aligned without post-processing.
  • Workflows can run from the command line, and connect to other programs through sockets or C#.

Weaknesses

  • One workflow in one process on one PC is the normal shape; it is not a multi-process graph.
  • Windows and .NET first, which does not match our Python and MATLAB code.
  • Visual workflows are harder to review, diff, and test than text.
  • Harp's clock guarantee covers Harp devices only; cameras and vendor programs still need another method.

ezmsg

A pure-Python pub/sub framework for signal-processing pipelines, derived from labgraph.

Strengths

  • Installs with pip, with no compiler.
  • Faster than ROS 2's Python client for 1 to 8 MB arrays (1.2 to 5 times on the Mac, 4 to 7 times on Linux).
  • Inside one process, messages pass by reference in about 0.1 ms at any size.
  • Ready-made signal-processing units and an LSL bridge.

Weaknesses

  • Python only, with no typed cross-language contract.
  • No MCAP recording and no Foxglove.
  • No advantage for small messages, and worse tail latency in our test.
  • The stable release (3.9.0) does not run on Python 3.14, the Python of our rig workspace.
  • A small project (about 30 GitHub stars).

Also looked at

Two more Python packages came up. Neither changes the picture, so they are not in the table above.

Timeflux

A Python framework for acquiring and processing biosignals (EEG, ECG, EMG) in real time, aimed at brain-computer interfaces and biofeedback.

  • Relevant, modestly popular. It sits in the same niche as ezmsg: about 190 GitHub stars, MIT license, runs on Linux, macOS, and Windows.
  • Quiet. The last release (0.17.2) was in December 2024.
  • For our rigs: it offers nothing that ezmsg or LSL does not, and it shares their limits (Python only, no typed contract, no MCAP).

streamz

A Python library for building pipelines over continuous streams of data, with branching, joining, flow control, and back pressure. It can work with pandas dataframes.

  • Popular, but a different kind of tool. About 1,300 GitHub stars, BSD license, latest release 0.6.6 in April 2026 after no releases between 2022 and late 2025.
  • It is a library for processing inside one Python program. It does not connect devices or programs, align clocks, or record. Its closest relative here is the reactive core of Bonsai.
  • For our rigs: it could be used inside a single node for stream logic, like any other library. It is not a candidate for the rig graph.

Similarities and differences

  • All four are publish/subscribe. A source produces a stream and any number of consumers read it. The ideas transfer even where the code does not.
  • rmw_iceoryx is not a fifth framework. It is ROS 2 with a different transport, so it shares ROS 2's contract and tools and differs only in how bytes move: zero copy on one host, against shared memory plus network with rmw_zenoh.
  • They differ in where the boundary sits. ROS 2 and LSL connect separate programs, possibly on separate machines. Bonsai and ezmsg mainly connect steps inside one program.
  • They differ in what they treat as the hard problem. ROS 2: a typed contract between many processes. LSL: time alignment and one recording. Harp: hardware timestamps. Bonsai: fast assembly of an experiment. ezmsg: array throughput in Python.
  • Only ROS 2 and Harp handle device control. LSL and ezmsg move data and leave commands to you.
  • Each has its own recording format. None writes NWB, the standard format for sharing neurophysiology data, so a conversion step is needed in every case.
  • They combine at the edges. An LSL stream, a Harp device, or a Bonsai workflow can be brought onto a ROS 2 graph by a small adapter, the same way our FicTrac and Kinefly adapters work.

Practices to adopt

Each practice is marked with where our rigs stand today, based on the rig-nodes contract (CONTRACT.md, package set 0.4.0).

  • In place
    Stamp data at the source and keep every clock. Each record keeps the device's own timestamp and the adapter's wall and monotonic receive times. No timestamp is rewritten. Shared with LSL and Harp. Contract §3 and §6 (three clock domains).
  • In place
    Record the raw device output beside the parsed form. The adapters publish each device record untouched, so a parsing error can be fixed after the experiment. Contract §2 (/<src>/raw).
  • In place
    Version the message contract and record the version with every run. One package-set version covers the messages and the nodes, and a consumer records it with each run. Contract §7.
  • In place
    Give every device a simulator and a conformance test. FicTrac, Kinefly, and BIAS each have a simulator, and the device-node test runs them through the real nodes. Common in ROS projects; rare in the neuroscience tools above.
  • Partly
    Bring other ecosystems in through adapters, not a second framework. This is how FicTrac, Kinefly, and BIAS join the graph. The same pattern should cover a future LSL stream, Harp device, or Bonsai workflow. No such adapter exists yet. Avoids two contracts and two recordings.
  • Partly
    Put speed where it is needed: C++ or in-process, not new middleware. Measured: a C++ subscriber on our graph beats ezmsg, and in-process hand-off beats both. No rig node uses either yet, because current traffic is small messages. A zero-copy transport such as rmw_iceoryx only pays off once the nodes are C++ and the frame type is fixed-size; measured, it then delivers 8 MB in 0.13 ms. From the ezmsg comparison and the ww18 benchmarks.
  • Not yet
    Measure and log clock offsets between machines; align offline. Our graph is limited to one host until this exists. LSL's method is the model: exchange short packets every few seconds, store every offset measurement in the recording, and fit the mapping afterwards. From LSL. Contract §1 names this as open (checklist item 7).
  • Not yet
    Use a shared hardware signal as ground truth for timing. A pulse or clock line recorded by every acquisition system lets software alignment be checked, and corrects devices that software cannot reach. The contract does not yet require one. From Harp (shared clock line) and LSL's own guidance (shared pulse).
  • Not yet
    Record each device's known constant latency as metadata. A fixed lag, such as camera exposure to timestamp, belongs in the recording so analysis can subtract it. From LSL (a header field for constant lag).
  • Not yet
    Describe each device in a machine-readable file. Harp defines common registers for every device. Our message files cover data, but commands and status are JSON described in prose. From Harp.
  • Not yet
